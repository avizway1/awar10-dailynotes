ECR : ECR is a fully managed container image registry service. We can securely store our container images, same as Docker Hub or OCI images. 
Native AWS Integration: The advantage with ECR is that we can use an IAM role to pull images from various services like EC2, ECS, and EKS. 


ECS Cluster : this is a place all of our workload is going to be scheduled to run or where our actual workload runs. 

--> AWS Fargate: fully managed serverless compute provider. We just need to pay per usage, generally for vCPUs and memory per second. If we don't want to have underlying access to any of the OS-level components and if we are not thinking about creating and managing servers, then this Fargate is a great choice for us. 

EC2 Launch Types: 
	1. Managed Instances: AWS will manage the patching and scaling of these EC2 instances on our behalf while we give configuration about the instance size. 
	2. Self Managed Instances: we must ensure the instance is patched and scaled. As it is a self-managed instance, it is our responsibility and we will have full control over the instance. 

---

Task : Container : this is similar to a container. It doesn't have auto-scaling and auto-healing capabilities. 

Service : a service is nothing but a group of tasks. We can integrate these tasks with a load balancer and an auto-scaling group. If a task is down, the service will ensure that the other task will be created or replaced without any delays. 

---

Task Definition : we can define how much CPU we want to provide to a task, how much memory we want to provide to the task, and where the actual image is. Those all will be present in the task definition.

Task Execution role: A task execution IAM role is used by the container agent to make AWS API requests on your behalf. Mainly pulls the image from ECR service. 

Task Role: If our container want to access any of th aws services i.e; s3/dynamodb.. We can create a role and attach here.. 


Essential container: 

YES: if any container has failed in the task, the entire task will be marked as failed. All other containers will stop. 
No: if any of the containers has failed, the remaining containers work normally. The task won't stop.

Capstone on ECS: 

1. Create a VPC with two public subnets and two private subnets, no NAT gateway, and an S3 endpoint.
 
2. Create other additional endpoints to pull the ECR image from the repository to the task. For that we should have four endpoints:
	- ECR DKR endpoint (Docker Registry)
	- ECR API endpoint (Authentication)
	- Logs (CloudWatch)
	- S3 gateway endpoint  (image layers)
	- ElasticFileSystem / EFS EP
	- DynamoDB Endpoint

3. Create EFS in our custom VPC to store all our web content and we are going to mount this to the /usr/share/nginx/html/ path. 

3.1 create accesspoint for EFS

aws efs create-access-point \
  --region ap-south-1 \
  --file-system-id fs-04a7d3955262bed26 \
  --posix-user Uid=101,Gid=101 \
  --root-directory 'Path=/site,CreationInfo={OwnerUid=101,OwnerGid=101,Permissions=0755}' \
  --tags Key=Name,Value=todo-web-ap


4. Prepare the dynamodb table to store the task information
	Table Name: Tasks
	Primary key: id		(string)

5. Use the dockerfile, then build and push it to ECR service service

6. Create 2 SGs for ECS tasks and EFS Service. 

ELB-SG --> http:80, https:443 : Anywhere
ECS-TASK-SG --> http: 80 --> Capstone-ELB-SG
EFS-SG --> NFS: 2049 --> ECS-TASK-SG

7. Create a Task Role and make sure to add DYNAMODB permissions on that role.. Also, Include ssmmessages permisisons for ecs-exec
--> add efs-access also.

8. Create task definition, make sure to add role, efs volume to the container.

9. Create ECS Cluster, make sure to enable monitpring. 

10. Create a Loadbalanacer and make sure to add http and https at listerner and atatch your domain name with ACM SSL Certificate.
